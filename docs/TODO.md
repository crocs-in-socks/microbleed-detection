# TODO / revisit

A running list of deferred decisions and follow-ups to review at the end of the restructuring work.

## CLI

- **Restore expected-error handling.** We removed the `domain_errors` context manager, the `EXPECTED_ERRORS` tuple, and the module `logger` from `cli/utils.py`, along with the `with domain_errors():` wrappers around each pipeline `.execute()` call in the command modules. Pipeline/core exceptions (`ValueError`, `FileNotFoundError`, `EnvironmentError`) now surface as tracebacks instead of clean, formatted CLI errors with a nonzero exit. Revisit how we want expected, user-actionable errors reported (and how that interacts with the `--verbose`/`--quiet` logging levels).

- **Reconsider the per-command file layout.** ✅ Done. The five per-command modules under `cli/commands/` collapsed into a single `cli/commands.py`: every command is now generated by `build_command` from a `CommandSpec` in the `SPECS` table (name, help, config model, pipeline module, precondition callable, dry-run/success message builders). Preconditions use shared `require_file`/`require_dir` helpers in `cli/utils.py`. The pipeline is imported by module name inside the generated body, so `--help`/`describe` still never import torch (verified). `entrypoint.py` registers commands by iterating `SPECS` and derives the `describe` name→config map from them.

- **Revisit how the `evaluate` command works.** ✅ Done. `evaluate` is now dataset-driven and end-to-end: it reads the dataset's raw manifest, infers each subject (checkpoints resolved from the training `experiment_dir` via `ExperimentLayout`, or passed explicitly for pretrained weights), and scores the source-space predictions against the manifest's reference masks. `execute()` now takes the config object like every other pipe, and `EvaluateConfig` moved to `orchestration/configs.py`; `cli/datamodels.py` only re-exports. The old inline `EvaluationSubject` list is gone (it's now an internal prediction/reference pairing in `evaluate.py`). Inference execution loads models for its one volume, while evaluation loads models once and calls `predict_and_write` for each subject. Possible follow-up: let evaluate target a specific split (e.g. an experiment's `split.json`) rather than the whole dataset.

  - **Hoist the "dataset has a scorable subject" check to the CLI precondition (during the rework).** Mirrors the fix applied to `train` (where the CLI precondition `validate_train` now reads the preprocessed manifest and rejects maskless subjects before the pipe runs). `evaluate` has the same shape but is deferred until the whole command is reworked: `_predict_dataset` in `evaluate.py` only raises `no subjects with reference masks to evaluate` *after* `execute()` has seeded, written `provenance.json`, and loaded both the detector and student — whereas `validate_evaluate` only checks that `raw.json` and the checkpoints exist. The cheap "at least one subject carries a reference mask" guard belongs in `validate_evaluate` so a non-scorable dataset fails fast. Important nuance vs. train: evaluate *intentionally* tolerates some maskless subjects (it skips them with a warning and only fails when none remain), so that skip-and-warn logic stays in the pipe — only the ">=1 mask exists" guard moves to the precondition, and the pipe's `if not scored: raise` stays as a defensive backstop. As with train, wrap the precondition's `read_manifest` so a malformed manifest surfaces as a clean `typer.BadParameter` rather than a traceback.

## Orchestration

- **`index-data` re-run behavior.** ✅ Done. Re-running `index-data` against an existing dataset directory used to silently clobber the manifest. It now accumulates: `execute` reads the existing `RawDatasetManifest` (if any), and `merge_source` appends the run's `RawSource` and merges its subjects, preserving the original `created_at` and bumping `updated_at`. Subject IDs stay globally unique — a collision with an already-indexed subject is a hard error before any write (the atomic write happens last, so a rejected run leaves the manifest intact). An optional `IndexDataConfig.source_id` (validated to `[A-Za-z0-9_-]+`, since it becomes part of on-disk paths) namespaces a source's IDs as `{source_id}_{subject_id}`; it's recorded on `RawSource`. Note: re-indexing the *same* source now errors (its IDs collide with the prior run) — there is no idempotent re-run or in-place source update, which would be the "replace" semantics we set aside.

- **Act on the `running`/`failed` manifest states, or drop them.** `ManifestStatus` has three states, but only the `complete` gate is currently used: `read_manifest(require_complete=True)` refuses any non-`complete` manifest, which correctly stops a downstream stage from consuming partial/failed upstream output. The `running` and `failed` states are *written* richly by training (`_run_stage` writes `running` before `trainer.fit`, then `complete` on success or `failed` with the error on a crash) but are never *read* to make a decision — nothing inspects a `running`/`failed` training manifest to resume, retry, or skip a stage. Either build the resume/retry logic that consumes these states (the natural companion to the write-once `SplitManifest`), or simplify the enum to just the distinction we actually act on. Until then the lifecycle is latent capability, not realized value.

- **Rework `orchestration/utils.py`.** ✅ Done. The patching helpers moved into a new `orchestration/patching.py` as a `Patcher` class hierarchy: a base `Patcher` owns subject resolution (paths → arrays), the maskless-subject guard, materialization, and `collect` (accumulate `PatchRecord`s across subjects), while `NonOverlappingPatcher`/`TargetCenteredPatcher` implement only `_extract`. The target-centered subclass owns its detector construction inputs and loads the checkpoint lazily on first extraction, then is dropped before model fitting so its GPU memory is reclaimed. `load_array` moved to `patching.py` (its only consumer). `utils.py` is now just the torch-touching teardown helpers (`release_gpu_memory`/`delete_model`) — a coherent module. `patching.py` imports torch, so the torch-free guarantee (configs/layouts/CLI) was re-verified.

## Data models / layering

- **Orchestration data models.** ✅ Done. The models the orchestration layer owns are split across flat files at its root: `layouts.py` (`DatasetLayout`, `ExperimentLayout`), `configs.py` (`SUBJECT_ID_PLACEHOLDER` plus `IndexDataConfig`, `PreprocessConfig`, `TrainConfig`, `InferConfig`, `EvaluationSubject` — consumed verbatim, each `execute()` takes its config whole), `manifests.py` (the manifest models and their read/write helpers together), and `records.py` (`PredictionSummary`). The CLI re-imports the configs from `orchestration.configs`, so no pipe imports from `cli` and the `cli → orchestration` dependency direction holds. Only `EvaluateConfig` remains in `cli/datamodels.py` (see the evaluate follow-up above).

## Core

- **Reconsider the `cast()` sites in `core/engines/processor.py`.** The module uses ~15 `typing.cast` calls to reconcile nibabel's loose types (e.g. `shape` as `tuple[int, ...]`, `affine` as `ndarray | None`) with the fixed types the `datamodels` dataclasses declare. These are static type-checker hints, not runtime conversions — the name reads misleadingly like coercion (a comment now flags this at the first site). The real invariants are enforced when the values feed `CropTransform`/`ImageGeometry`, whose validators check shape and affine. Consider replacing the bare casts that feed those dataclasses (the `source_shape`/`source_affine` pair especially) with small checked helpers (e.g. `_as_shape3`, `_require_affine`) that narrow *and* validate in one place, so the type guarantee and the runtime check live together and failures point at the actual culprit (a non-3-D input) rather than at a generic `CropTransform` error. Scope it: some casts (e.g. `crop_start`/`crop_stop` derived from an already-validated bounding box) are pure length-narrowing where a runtime check is redundant.

- **Reconsider the on-disk patch storage format.** ✅ Done. Switched from one `.npz` per patch (thousands of tiny files) to **per-subject memory-mapped `.npy` stacks**: `materialize_patches` stacks a subject's fixed-shape patches into `volumes_{id}.npy` + `masks_{id}.npy` (each `(N, P, P, P)`), written atomically (temp file + `os.replace`), and emits one `PatchRecord(volume_path, mask_path, patch_index, has_microbleed)` per patch. `datasets.py` opens each array with `np.load(mmap_mode="r")`, caches the mmap by path (lazily, so DataLoader workers each build their own after the fork — no shared handles), and slices one patch by `patch_index` (copied out so augmentation can write in place). File count dropped from `2*patches` to `2*subjects`; random access stays O(1) via the OS page cache; store-once inflation preserved (duplicate records share file+index). **The per-read SHA256 checksum was dropped** — it re-hashed the whole file on every `__getitem__`, which defeats mmap, and atomic writes already prevent torn/partial files (the main thing it guarded); bit-rot/tamper within a run is low-value to guard here. `PatchRecord`'s `checksum` field and the corrupt-file `ValueError` are gone. No test pinned checksum behavior. Uncompressed still (float patches compress poorly, and it avoids per-read DEFLATE).

- **Patcher factory indirection.** ✅ Done. `_run_stage` now receives a concrete `Patcher`. `TargetCenteredPatcher` defers detector construction until its first extraction, which stays inside `_run_stage`'s `try` and allows the patcher, including its detector, to be dropped before `fit`. Also revisit the two "why" questions raised alongside this: (1) why target-centered patching labels the candidate mask and walks `regionprops` to center a patch per connected component, and (2) whether the three separate patch batch dataclasses (`SegmentationBatch`/`SegmentationClassificationBatch`/`ClassificationBatch`) are each pulling their weight or could collapse.

- **Revisit `patch.py` and `augmentations.py` placement in `core/transforms/`.** ⏸ Parked, still not settled. `core` is intended as a portable, reusable library (trainers/evaluators/processors/transforms liftable into a future project), so `transforms/` is kept as a coherent image-operations package rather than reorganized around this app's pipeline stages — that's why `frst.py` (a per-forward-pass model-input transform used at train *and* infer time, not a stored preprocess step) also stays here. Under that library lens both `patch` (spatial windowing) and `augmentations` (stochastic train-time augmentation) are arguably legitimate transforms (cf. torchvision/MONAI keeping augmentations in `transforms`). But each has exactly one consumer today (`dataloading/patchers.py` and `dataloading/datasets.py` respectively), which argues they belong in `dataloading/`. Folding `augmentations` into the volume-ops module was considered and rejected: its sampling/composition policy is config- and RNG-bound, training-only, and cohesive — dissolving it would recreate a grab-bag and drag a config/RNG dependency into the deterministic preprocessing ops. Decision deferred until a second project reveals the real seams (avoid premature generalization). Note the split naming question too: whether `volume_ops.py` should eventually break into `spatial.py`/`intensity.py`/external-tool ops — same "wait for a second consumer" reasoning.
